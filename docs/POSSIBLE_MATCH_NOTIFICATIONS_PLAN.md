## 1. Problem

The exhausted deck currently promises:

> “You have seen all the top matches, we will notify you if a new match is found.”

That promise is false:

- `AppNotificationKind` has only `connection_request`, `request_accepted`,
  `request_declined`, `feedback_ready`, `skill_moderation`, `unknown`
  (`lib/models/app_notification.dart`).
- `NotificationPresenter.showMatch` only fires for accepted requests.
- No job recomputes decks in the background.
- Matching is request-time only. `cache_is_fresh()` cannot detect a **new**
  candidate entering a viewer’s pool.
- Embedding regeneration is best-effort and caller-only
  (`lib/services/profile_service.dart:419-440,1156-1161`;
  `supabase/functions/get-matches/index.ts:216-233`).

Option 2 closes that gap with a bounded, event-driven fan-out pipeline.

## 2. Current system facts

### Matching

- `get-matches` retrieves candidates from `profile_embeddings` via
  `match_candidates()` (pgvector + skills fallback).
- It reranks only the retrieved shortlist (`A` for all, `B` for top 10), never
  all live accounts.
- `match_cache` is per viewer + `as_role`.
- `cache_is_fresh()` checks config revision, viewer profile/skills updates, and
  updates of **candidates already in the cached deck**. It cannot discover a new
  candidate.
- Client deck TTL is 10 minutes, with stale-while-revalidate
  (`lib/services/match_api.dart:371-425`). The backend cache has no max age.
- `profile_embeddings` has one HNSW index on `embedding` and a btree
  `(role, field_group, input_type)`.

### Embeddings

- Required vectors: mentor/learner × skills/context × passage/query = 8 per
  profile.
- Generated by `generate-embeddings` for the **calling user only**.
- Onboarding awaits the call; profile edits fire-and-forget it.
- Failures are swallowed. No retry/reconciliation.
- At the time of planning, 14 onboarded profiles have no vectors. The admin
  metric is correct.
- Notification fan-out must not run on missing/stale vectors.

### Notifications

- `notifications` table: `user_id`, `kind`, `payload jsonb`, `read_at`,
  `created_at`.
- `notifications_kind_check` must be extended.
- `notify(p_user, p_kind, p_payload)` inserts a row.
- `list_notifications()` joins connection/profile data for the existing kinds.
- Realtime insert delivery already exists through `NotificationService`.
- Local notification channel is `Requests & matches`.
- `notificationKindEnabled()` maps kinds to local preferences.
- `ActivityFilter` currently has All, Unread, Requests, Updates.

### Available infrastructure

- `pg_cron` 1.6.4
- `pg_net` 0.20.4
- `supabase_vault` 0.3.1
- Existing cron job pattern for `moderate-notes` using `net.http_post` + Vault
  secret. This plan does **not** need an Edge Function or a worker secret.

## 3. Chosen architecture

**SQL-first, database-native fan-out.**

```text
profile / user_skills / showcase change
        │
        ▼
possible_match_jobs (debounced, one active job per candidate)
        │  pg_cron every minute
        ▼
process_possible_match_jobs()
  ├─ validate candidate + vector freshness
  ├─ reverse ANN lookup: likely viewers
  ├─ filter blocks/connections/reports/cache/caps
  ├─ dedupe + cooldown
  └─ insert notifications(kind='possible_match')
        │
        ▼
Realtime → in-app activity banner + local notification
```

No Edge Function is required for the core path. This removes network/worker
secret failure modes and keeps the transaction local. It also means the feature
depends on embeddings already being fresh; stale jobs retry instead of notifying
on bad vectors.

### Why not the alternatives

| Approach | Why rejected |
|---|---|
| Recompute every viewer’s full deck on each profile edit | O(N × NIM calls); slow and expensive |
| Rerank all live accounts on every request | Not how the matcher works; unacceptable cost |
| Client-side trigger only | Unreliable, can be closed mid-request |
| Notify every embedding update | Spam; duplicate/self/stale candidates |
| Pairwise O(N²) comparison | Unbounded and unnecessary |
| Full mutual match before notify | Requires both users’ complete reciprocal rerank; too costly for a notification |

**Product semantics:** this is a **possible match suggestion**, not a confirmed
mutual match. Copy must say “matches your interest,” not “you matched.”

Notification SLA: **1–2 minutes** after the edit and successful embedding, not
instant. If instant is required later, add a fast-path `pg_net` call from the
enqueue trigger; keep cron as the retry path.

## 4. Data model

Create migration `supabase/migrations/20261120000400_possible_match_jobs.sql`.

### `possible_match_jobs`

```sql
create table public.possible_match_jobs (
  id bigserial primary key,
  candidate_id uuid not null references public.profiles(id) on delete cascade,
  reason text not null default 'profile_update'
    check (reason in ('new_profile','profile_update','skills','context','media','manual')),
  status text not null default 'pending'
    check (status in ('pending','processing','done','failed','skipped')),
  attempts integer not null default 0,
  run_after timestamptz not null default now(),
  locked_at timestamptz,
  last_error text,
  notifications_created integer not null default 0,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create unique index possible_match_jobs_active
  on public.possible_match_jobs (candidate_id)
  where status in ('pending','processing');

create index possible_match_jobs_due
  on public.possible_match_jobs (run_after)
  where status = 'pending';

create index possible_match_jobs_created
  on public.possible_match_jobs (created_at desc);
```

### `possible_match_events`

One row per recipient/candidate pair. Used for dedupe, cooldown, shadow mode,
and traceability.

```sql
create table public.possible_match_events (
  id bigserial primary key,
  recipient_id uuid not null references public.profiles(id) on delete cascade,
  candidate_id uuid not null references public.profiles(id) on delete cascade,
  as_role public.embed_role not null,
  score real not null default 0,
  skill_name text,
  skill_path text,
  status text not null default 'shadow'
    check (status in ('shadow','notified','suppressed')),
  suppressed_reason text,
  last_notified_at timestamptz,
  notification_id uuid references public.notifications(id) on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (recipient_id, candidate_id)
);

create index possible_match_events_candidate
  on public.possible_match_events (candidate_id, created_at desc);
create index possible_match_events_recipient
  on public.possible_match_events (recipient_id, last_notified_at desc);
```

RLS enabled, no anon/authenticated grants, service/postgres only. SQL cron runs
as the database owner.

### `notifications`

Extend the check constraint:

alter table public.notifications drop constraint notifications_kind_check;

    'connection_request','request_accepted','request_declined',

## 5. Enqueue design

Create `public.enqueue_possible_match_job(p_candidate uuid, p_reason text)`:

- Skip if candidate is missing or `has_completed_onboarding = false`.
- Upsert one active job per candidate:
  - pending/processing row → update `run_after = now() + 45 seconds`,
    `reason`, `updated_at`.
  - otherwise insert a new pending job.
- Debounce coalesces profile + user_skills + showcase writes in the same edit.
- **Do not** enqueue from admin taxonomy changes (`skill_nodes`); mass skill
  edits would create notification storms. Cache invalidation remains separate.

### Triggers

- `user_skills` AFTER INSERT/UPDATE/DELETE → enqueue the affected `user_id`.
- `profiles` AFTER UPDATE OF `role`, `languages`, `teaching_styles`,
  `learning_styles`, `availability`, `has_completed_onboarding`,
  `moderation_status`, `photos`, `teaching_skill_images` → enqueue.
  - Do **not** trigger on `learning_skills`/`teaching_skills`: those are synced
    from `user_skills` and would double-enqueue.
  - Do not trigger on `last_seen_at`, presence, read receipts, etc.
- `skill_showcases` AFTER INSERT/DELETE → enqueue owning profile. This makes
  first-media eligibility notify-capable for mentor discovery.
- `user_skill_notes` changes will normally surface through `user_skills`; verify
  note approval updates `user_skills.note_approved` or add a trigger if not.

### Eligibility at processing time

A candidate is eligible when:

- profile exists and `has_completed_onboarding`
- `moderation_status = 'active'`
- has at least one teach/learn skill appropriate to the direction
- for mentor discovery, `has_discovery_media(candidate)` is true
- embeddings exist and are newer than the relevant profile/user_skills writes
- candidate has not been deleted/suspended/banned

If vectors are missing/stale, do not notify. Retry with backoff; after max
attempts mark failed with `embeddings_not_fresh`.

## 6. Reverse recipient query

Create `public.possible_match_recipients(p_candidate uuid, p_limit int default 250)`
returning:

```text
recipient_id uuid
as_role embed_role      -- viewer's target role
score real
skill_name text
skill_path text
source text             -- 'embedding' | 'skill_fallback'
```

### Direction A — candidate as mentor

- Candidate vectors: `role='mentor'`, `input_type='passage'`
  (`skills` + `context`).
- Viewer vectors: `role='learner'`, `input_type='query'`.
- Candidate may have role `mentor` or `both`.

### Direction B — candidate as learner

- Candidate vectors: `role='learner'`, `input_type='passage'`.
- Viewer vectors: `role='mentor'`, `input_type='query'`.
- Candidate may have role `learner` or `both`.

### Score

Use the same configured weights as production:

```text
score = w_skills * (1 - cosine(candidate_skills, viewer_skills))
      + w_context * (1 - cosine(candidate_context, viewer_context))
```

Read weights from `pipeline_config.embedding_weights`; default `0.7/0.3`.
Only compare vectors of matching role and field group.

### Skill fallback

For viewers without embeddings, optionally union exact/ancestor skill overlap:

- candidate `teach` skill ↔ viewer `learn` skill
- candidate `learn` skill ↔ viewer `teach` skill

Use `skill_nodes.path` ltree ancestry only when exact `skill_id` yields no
embedding match. Give fallback a lower priority and keep it behind
`possible_match_skill_fallback` (default true only during rollout).

### Filters (must be applied in SQL)

Exclude when:

- recipient = candidate
- recipient not onboarded, not active, or suspended/banned
- candidate not eligible (moderation/media/role)
- either direction blocked
- any connection exists in either direction (pending, accepted, declined, or
  unmatched — do not re-notify after a decline)
- either direction reported
- candidate already exists in recipient’s `match_cache` for that `as_role`
  (they already have them in the current deck)
- a `possible_match_events` row exists with `last_notified_at` inside the
  cooldown (default 60 days)
- recipient exceeded daily/weekly caps
- score below `possible_match_min_score` (initial default: tune after shadow
  data; start at `0.12`, review distribution)
- optional: recipient’s last_seen is older than 90 days (recommended for local
  notifications; in-app activity can still be retained)

Return the highest score per recipient across both directions. Limit to
`possible_match_recipients_per_job` (default 100).

### HNSW caveat

The existing HNSW index is not partitioned by role/field. Filtered ANN queries
can fall back to scans or lose recall. Before enabling, run `EXPLAIN ANALYZE` on
the recipient query. If needed, add partial indexes:

```sql
create index idx_embed_q_learner_skills on public.profile_embeddings
  using hnsw (embedding vector_cosine_ops)
  where input_type = 'query' and role = 'learner' and field_group = 'skills';
-- repeat for learner/context, mentor/skills, mentor/context
```

Do not add all four without measuring write/storage cost. At current scale (88
vectors) an exact scan is fine; the index matters at thousands+.

## 7. Worker logic

Create migration `supabase/migrations/20261120000500_possible_match_fanout.sql`.

### Functions

1. `claim_possible_match_jobs(p_limit int)`
   - `FOR UPDATE SKIP LOCKED`
   - selects due `pending` jobs
   - marks `processing`, increments attempts, sets `locked_at`
   - returns claimed rows

2. `process_possible_match_jobs(p_limit int default 20) returns jsonb`
   - **reap** processing jobs older than 5 minutes back to pending with backoff
   - read config:
     - `possible_match_enabled`
     - `possible_match_mode` (`off`, `shadow`, `live`)
     - cap/cooldown/min score values
   - if disabled/off: return without claiming
   - claim jobs
   - for each job:
     - validate candidate + embedding freshness
     - get recipients
     - for each recipient:
       - apply per-recipient caps
       - insert/update `possible_match_events`
       - in `shadow`: store `status='shadow'`, no notification
       - in `live`: insert `notifications(kind='possible_match')`, set
         `status='notified'`, `notification_id`
       - `suppressed`: store reason (`cap`, `connected`, `blocked`, `in_cache`,
         `cooldown`, `low_score`, `inactive`)
     - mark job done/skipped
   - on error: attempts++, exponential backoff, failed after 5
   - return counts `{claimed, candidates, notified, suppressed, failed}`

3. `emit_possible_match_notification(p_recipient, p_candidate, p_role, p_score,
   p_skill_name, p_skill_path, p_reason)`
   - re-check connect/block/report/candidate eligibility inside the transaction
   - enforce cooldown/caps under an advisory lock per recipient
   - upsert `possible_match_events` by pair
   - insert `notifications` only when allowed
   - payload:

```json
{
  "candidate_id": "<uuid>",
  "as_role": "mentor",
  "score": 0.42,
  "skill_name": "Filipino Cooking",
  "skill_path": "cooking_culinary.filipino_cooking",
  "reason": "profile_update"
}
```

Never put email, notes, bio, or private fields in the payload.

### Caps

Recommended initial values:

| Config | Default |
|---|---|
| `possible_match_recipients_per_job` | 100 |
| `possible_match_jobs_per_run` | 20 |
| `possible_match_min_score` | 0.12 (tune in shadow) |
| `possible_match_cooldown_days` | 60 |
| `possible_match_daily_cap` | 3 |
| `possible_match_weekly_cap` | 10 |
| `possible_match_max_attempts` | 5 |
| `possible_match_skill_fallback` | true (shadow only initially) |

Per-recipient caps are checked against `notifications` kind `possible_match`
inside a rolling 24h/7d window.

### Cron

```sql
select cron.schedule(
  'possible-match-fanout',
  '* * * * *',
  $$select public.process_possible_match_jobs(20)$$
);
```

The job is idempotent; every invocation reaps stale claims. It does not use
`pg_net`.

## 10. Edge cases and logic flaws

### Candidate-side

- [ ] Missing/stale embeddings → retry, never notify.
- [ ] Failed NIM embed → retry/backoff; no false notification.
- [ ] Onboarding incomplete → skip.
- [ ] Suspended/banned/deleted → skip and cleanup existing.
- [ ] Mentor without discovery media → skip.
- [ ] Skill becomes pending/unapproved → skip.
- [ ] Candidate edits multiple times in 45s → one coalesced job.
- [ ] Candidate edits photo/name/bio only → no embedding change; do not notify
      unless media eligibility changed false→true.
- [ ] Candidate has both roles → consider both directions, one event per pair.
- [ ] Candidate is already in recipient cache → do not call it “new.”
- [ ] Admin taxonomy merge/retire → no candidate notifications; only cache
      invalidation. Avoid mass notification storms.
- [ ] Candidate re-adds same skill after removing it → pair cooldown applies.

### Recipient-side

- [ ] Already connected/request pending/accepted/declined → skip.
- [ ] Blocked either direction → skip + cleanup.
- [ ] Reported either direction → skip + cleanup.
- [ ] Not onboarded/inactive/suspended → skip.
- [ ] Notification preference disabled → do not show local notification; decide
      whether in-app activity still records it (current behavior records other
      kinds; for possible_match, server cannot see local prefs, so record it but
      suppress local presentation).
- [ ] Quiet hours → local notification suppressed; in-app row remains.
- [ ] Daily/weekly caps → suppress.
- [ ] Pair cooldown → suppress.
- [ ] More than 100/250 recipients per candidate → only top scored; document
      fairness/coverage.
- [ ] Recipient has no embeddings → optional skill fallback only; do not claim
      semantic confidence.
- [ ] Multiple candidate jobs same minute → per-recipient caps serialize.
- [ ] App not installed/open → in-app row persists for next open; no remote push.
- [ ] Candidate deleted before tap → fallback copy.
- [ ] Recipient has already seen the candidate locally (`SeenDeckService`) but
      server cache doesn’t know → possible duplicate. Consider adding a
      server-side seen/dismissed signal later; do not block phase 1 on it.
- [ ] Notification read/unread and clear-read behavior matches existing kinds.
- [ ] Activity filter “Requests” must not include possible matches.
- [ ] Possible-match rows should not increment the Requests badge; use the
      activity/bell badge only.
- [ ] Repeated candidate edits must not spam: one active job + pair cooldown +
      per-recipient caps.

### Pipeline/concurrency

- [ ] Two workers run cron simultaneously → `FOR UPDATE SKIP LOCKED`.
- [ ] Worker crashes while processing → reaper after 5 minutes.
- [ ] Job attempt limit 5 with exponential backoff.
- [ ] Trigger fires during a transaction that later rolls back → job insert rolls
      back with it.
- [ ] Embedding update and job processing race → freshness check + retry.
- [ ] Null/empty candidate vectors → skip.
- [ ] Duplicate event insert under concurrency → unique pair + upsert.
- [ ] Notification insert succeeds but event update fails → wrap in a
      transaction or make event insert idempotent.
- [ ] Cron disabled/feature flag off → no jobs claimed and no notifications.
- [ ] Clock/timezone: use server `now()` consistently.
- [ ] Score NaN/out of range → clamp/ignore.
- [ ] HNSW filtered recall degradation → verify query plan.

## 11. Complexity analysis

### Rejected naive approach

Recomputing every viewer or reranking all live accounts per update:

```text
O(N viewers × NIM calls) per profile update
```

At 10k users this is thousands of network calls per edit. Rejected.

### Proposed per-job cost

For one candidate:

- up to 2 directions
- 2 field groups per direction
- 4 HNSW/ANN queries, each top `K` (default 200)
- one skill-overlap fallback query (optional)
- up to `R` recipient candidates (default 250) after filters
- up to 100 notification inserts
- small fixed dedupe/cap checks

Approximate:

```text
O(4 × K log N + K + R + inserted)
```

With `K=200`, `R=250`, this is bounded per job. A cron batch of 20 jobs/min is
bounded to ~5k pair checks/min before caps, and each pair performs indexed
existence checks.

### Scale notes

- At 50–1k users: exact scans or HNSW are trivial; keep caps conservative.
- At 10k users: HNSW + partial indexes likely needed; monitor p95 job duration.
- At 100k+ users: the candidate fan-out still works with top-K caps, but a
  single broad candidate (e.g., “Cooking”) may have thousands of plausible
  viewers. The top-N cap means most are never notified. Decide fairness policy:
  - newest active viewers first,
  - round-robin across batches,
  - or a separate “new profile” digest rather than per-candidate notifications.
- The work is **not** O(N²) globally, but it is O(updates × K) and can still be
  large if many users edit simultaneously. The job table and cron batch cap
  protect the database.
- `notifications` write amplification is bounded by recipient caps.
- HNSW index write cost grows with partial indexes. Measure insert latency for
  `profile_embeddings`.

### Complexity trap: filtered HNSW

A single global HNSW index queried with `role/field_group/input_type` filters
can lose recall or choose a seq scan. This is a correctness and performance
risk. Test with `EXPLAIN (ANALYZE, BUFFERS)`. If the plan is not ANN, add partial
HNSW indexes or split embedding storage; do not silently accept slow scans.

### Complexity trap: reverse vs forward ranking

Candidate-centric reverse lookup is an approximation. A candidate may score
highly for a viewer but still not appear in that viewer’s final top 10 after
reciprocal rerank. Therefore:

- call it “possible match”,
- use a threshold and recipient caps,
- do not promise “your next match” or “mutual match,”
- optionally re-check against the viewer’s `match_cache` threshold before notify.

## 12. Security and privacy

- Tables are service/postgres only; RLS enabled and no anon/authenticated
  grants.
- Notifications already belong to `user_id`; do not expose candidate email or
  notes.
- Use only public profile name/avatar/skill fields.
- Do not trust payload text in Flutter; render fixed strings.
- Worker runs as database owner via `pg_cron`; no new secret to leak.
- Rate-limit candidate updates and per-recipient notifications to prevent abuse
  (a user could otherwise edit skills repeatedly to spam).
- Reports/blocks/connections must suppress both generation and existing rows.
- Retention: keep read possible_match rows for 90 days, then delete; unread rows
  can follow existing activity retention.

## 15. Acceptance criteria

- User B receives at most one `possible_match` notification when A becomes a
  plausible match.
- No notification for blocked, connected, reported, cached, self, inactive, or
  unembedded candidates.
- Re-running the worker is idempotent.
- Repeated edits do not spam.
- In-app Activity shows the notification with candidate name/skill and opens the
  candidate profile.
- Local notification respects master/preference/quiet-hours settings.
- Exhausted deck copy is true when live mode is enabled.
- Job latency p95 ≤ 2 minutes at the tested scale.
- No production deck path is reranked for all accounts.

## 17. Decisions and remaining follow-ups

Resolved for this release:

1. **Score threshold:** started at `0.12`; live verification used scores
   `0.31`–`0.62`. Keep the config knob for tuning.
2. **Recipient fairness:** top-N by score per candidate (`recall_k=200`,
   `recipients_per_job=100`). Revisit at 10k+ users with a digest or round-robin.
3. **Profile tap UX:** reuse the existing public-profile card through
   `AppRouter.openUserProfile()`; no new profile page.
4. **Local notification channel:** reuse `Requests & matches`, as decided.
5. **Inactivity filter:** disabled (`possible_match_inactive_days=0`) so
   Activity remains available to returning users; local notifications still
   respect OS/app preferences.
6. **Fast path:** accepted the 1–2 minute cron SLA. No `pg_net` call.
7. **Embedding reconciliation:** one-off backfill completed; the worker retries
   missing/stale vectors with backoff and never notifies on them. A permanent
   server-side reconciliation job is still future work if client self-heal is
   not enough.
8. **Seen-but-not-connected:** still a known duplicate risk because the server
   does not know the local seen deck. Not blocking this release.

Remaining follow-ups:

- Add a permanent embedding reconciliation job (or service-role backfill) so
  dormant profiles do not depend on a client call.
- Revisit fairness and a digest at larger scale.
- Consider a separate "Match suggestions" OS channel if product wants granular
  channel control.
- Monitor `possible_match_jobs` / `possible_match_events` and `cron.job_run_details`
  after the first production week.
