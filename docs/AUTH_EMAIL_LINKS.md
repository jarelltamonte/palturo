# Auth email links and redirects

## Short answer

No separate backend is required. Supabase Auth is already the backend that
creates the reset token, stores the user, and sends the email. The GitHub domain
appears because the Supabase project's **Site URL** still points at the old
GitHub Pages auth page:

```
https://bogart123456.github.io/palturo-auth/
```

That value is used as the fallback destination for every auth email. Resend is
already configured as the SMTP provider and the recovery template is already
branded for PalTuro, so the email itself is not being generated by a second
system.

## Why the reset email looked like a confirmation email

The recovery template is correct (`Reset your password`, with a
`{{ .ConfirmationURL }}` button). The problem is where that URL lands:

1. Supabase verifies the recovery token.
2. It redirects to the `redirect_to` value if that value is allowlisted.
3. Otherwise it falls back to **Site URL** — currently the GitHub Pages page.
4. The GitHub Pages page is not the app's reset screen, so it reads like an
   email-confirmation or landing page.

On top of that, the Flutter client was sending a native deep link on web:

```
palturo://auth/reset-callback
```

Browsers cannot open a custom scheme, so the redirect was either rejected or
fell back to Site URL. The client now chooses the redirect by platform:

| Platform | Signup / resend | Password reset |
| --- | --- | --- |
| Web | current origin or `APP_PUBLIC_URL` | current origin or `APP_PUBLIC_URL` |
| Android / iOS | `palturo://auth/callback` | `palturo://auth/reset-callback` |

## Required Supabase dashboard settings

Open **Authentication → URL Configuration**.

1. **Site URL** — set this to the production web app, for example
   `https://palturo.app/`. Do not leave the GitHub Pages URL here.
2. **Redirect URLs** — add every origin that may receive an auth link:

   ```
   https://palturo.app
   https://palturo.app/**
   http://localhost:5317
   http://localhost:5317/**
   palturo://auth/callback
   palturo://auth/reset-callback
   ```

3. Keep the GitHub Pages URL only while that deployment is still in use.

The repository's `supabase/config.toml` uses the local origin for the Supabase
CLI. Production values live in the dashboard and are not read from this file.

## Production build

Pass the public origin so the redirect does not depend on where the build is
served:

```sh
flutter build web --release \
  --dart-define-from-file=.env \
  --dart-define=APP_PUBLIC_URL=https://palturo.app
```

For local development, leave `APP_PUBLIC_URL` empty and the app uses
`Uri.base.origin` (for example `http://localhost:5317/`).

## Email delivery

Resend is already the SMTP host and `team@palturo.app` is the sender. Confirm
that the `palturo.app` domain is verified in Resend with SPF and DKIM records,
otherwise deliverability will suffer even when the link is correct.

The recovery template is stored in **Authentication → Email Templates → Reset
Password**. The confirmation template is separate. Do not paste the reset
template into the confirmation slot.

## Domain prerequisite

`palturo.app` currently has no DNS record. Before changing **Site URL** to that
domain, deploy the web build to a host and point the domain at it. Changing Site
URL before DNS resolves would break confirmation and reset links for everyone.

If the production domain is `palturo.ph` or another host, use that value instead
everywhere in this document.

## Verification checklist

- [ ] Request a reset for a real account.
- [ ] The email subject is `Reset your PalTuro password`.
- [ ] The link host is the production domain, not `github.io` or `supabase.co`.
- [ ] The link opens the app on the reset form, not a confirmation page.
- [ ] A new password can be saved and the old password no longer works.
- [ ] Signup confirmation opens the app and confirms the account.
- [ ] Android/iOS reset links still open `palturo://auth/reset-callback`.
- [ ] Expired or reused links show the expired-reset screen.
