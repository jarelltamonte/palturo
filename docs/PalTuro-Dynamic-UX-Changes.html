1. Executive summary

This release turns PalTuro's notification layer into a complete dynamic UX system, then adds the day-to-day chat and list controls expected from a modern messaging product, and finally introduces privacy-controlled presence, typing, and read receipts.

What users can now do

  • See live request, match, feedback, moderation, and message events as non-blocking top banners, with a subtle match moment and an Activity inbox.
  • Control notifications by category, previews, quiet hours, sound, and vibration, and see honest permission state.
  • Receive local system notifications while the app is alive, including while backgrounded on Android, with tap and cold-start routing.
  • Refresh lists, work offline with a clear strip, see an app badge, and keep unsent drafts per chat.
  • Mute a chat, mark it unread, copy a message, search the thread, jump to the latest message, retry failed sends, and see the first unread divider.
  • Manage chats from a long-press sheet and triage Activity with filters, day groups, swipe-to-read, and clear-read.
  • Control online status, typing, and read receipts for Pals only; see Online/last-seen, typing dots, and Seen only when privacy allows.
Not shipped. Push delivery to killed or suspended apps (A5) remains blocked on Firebase/APNs/VAPID credentials. The app does not claim killed-app delivery or guaranteed iOS background delivery. See section 9.

7. Architecture and new modules

The work stays within the existing Flutter app and Supabase backend. Notifications have one typed source, one presenter, and one local delivery service; chat privacy/status lives on the profile and is exposed through RPCs; realtime chat topics are reused for presence, typing, and read events.

Services

NotificationPresenterChooses banner kind, applies category/quiet/preview/privacy gates, plays match/message feedback, suppresses the active screen.
LocalNotificationServiceSystem notifications, Android channels (four sound/vibration combinations per category), permission state/request, tap and cold-start routing.
AppBadgeServiceLauncher badge from activity + chat unread, preference gate, serialized writes, web no-op, sign-out reset.

SoundServiceShared player over messages/newmatch/splash assets, preference/lifecycle gates, debounce, serialized init.
AppShellStateSelected tab, Activity/Requests open flags for route-aware suppression.
AppRouter / navigatorKeyQueue-safe routing from services and cold starts.

Event flow

  • Server notification → notifications realtime insert → NotificationService (typed, deduped) → NotificationPresenter → top banner; Activity list and unread count update.
  • Foreground message → ChatStateService realtime → IncomingMessageEvent (outside the active room) → presenter → banner with sender + preview; local system notification only when not foreground.
  • Background/alive local notification → LocalNotificationService → Android channel chosen by category and sound/vibration → system notification → tap payload → AppRouter.
  • Chat topic → presence state (Online), typing broadcast (2s throttle/3s expiry), read broadcast (throttled, server-authoritative reload).

8. Database and server changes

Seven migrations were added and applied to the linked Supabase project. All functions are SECURITY DEFINER with a pinned search_path; writes are RPC-only; the notification and connection tables remain SELECT-scoped by RLS.

Security model

  • Notifications: authenticated can SELECT their own rows (notif_read); all writes go through SECURITY DEFINER RPCs (mark read, clear read).
  • Connections: authenticated can read only non-receipt columns; read timestamps are RPC-only. RLS limits rows to participants.
  • Connection preferences: SELECT-only for the owner; mute/unread writes go through validated RPCs.
  • Profiles: presence/typing/receipt columns have no direct client grants; status flows through touch_last_seen, set/get_chat_privacy, get_pals_presence, and get_conversations.
  • Status masking: only accepted connections receive presence/typing/receipt flags and timestamps; last_seen is null when presence is off; peer read_at is null when receipts are off.
Read receipts transport. Publishing connections would require table-wide SELECT for Realtime and would re-expose the read timestamps that C0 locked down. C3 therefore uses a read broadcast on the chat topic plus the 60s conversation refresh, which is server-authoritative and reconciles offline peers.

Notification delivery matrix

App backgrounded, process alive on AndroidLocal system notification (best effort), with tap routing.
App backgrounded on iOSNot guaranteed; the OS may suspend the app/socket.
App killed or force-closedNo notification until the app is reopened.
App reopened after missed eventsActivity, unread counts, and messages reconcile from the server.
Broadcast announcement to inactive usersNot delivered until the next app open.
Accepted gap (A5). Push to killed/suspended apps requires FCM/APNs/VAPID credentials. Do not claim killed-app alerts or guaranteed iOS background delivery in release notes. There is no data loss: notification rows, messages, and unread counts are server-backed.

Mute and unread

  • Mute durations: 1 hour, 8 hours, 1 day, 1 week, until turned back on; Unmute appears when muted.
  • Muted chats produce no banner or local notification; unread count and launcher badge still count them.
  • Mark unread is a server flag; the dot clears when the chat opens; opening also advances the server read cursor used for Seen.

Seen rules

  • Only the last own message can show Seen.
  • Seen requires the peer's read timestamp to be at or after that message's server created_at.
  • If the peer disabled read receipts, no timestamp is exposed and Seen is hidden.
  • Live read events trigger a server reload; the payload clock is never displayed.
